# AIxCoding 开发规范（iCode-fork 定制工程）

> 适用仓库：iCode-fork（上游：开源 chrys/iCode；定制标识：`aixcoding`）。
> 读者：全体开发成员与 AI 编码代理。本文件是唯一权威版本，随实践持续修订。
> 定位：本文是**开发总纲**——团队通用开发规则（R5–R8、R10–R11、工作流、文档管线）与 fork 特有规则（上游接触面治理：R1–R4、R9、清单与升级）合一的入口；各特性的详细方案、状态与历史在 `aixcoding/docs/` 下的活文档中，按需读取。
> **修订元规则**：本规范的"微改动豁免"（§6）与 README 速查表是落地性的一等公民。任何新增规则须先评估"是否加重这两条减压阀"（增加豁免判定的判断成本、加长速查路径）——完备性不得侵蚀简单易行；评估不过的，宁可把检查交给机器（脚本/CI）而不是加到人身上。
> **过渡期声明（2026-10-21 起）**：本文（含 R9/R10 与目录规则）描述目录重组完成后的**目标状态**；仓库现状与目标的差距及执行进度见 `aixcoding/docs/batches/restructure/plan.md`。过渡期内以本文为规范，新代码一律按目标状态落位。

## 1. 目标与核心认识

所有规则服务于一个目标：**最小化跟随上游升级的总成本**。

| 升级风险 | 表现 | 检测手段 |
|---|---|---|
| 文本冲突 | Git 合并失败 | git diff / merge |
| 结构冲突 | 定制依赖的上游 API 被删改 | 导入失败、类型检查、逐点核对 |
| 语义冲突 | 合并成功但行为悄然变化 | 定制测试集回归 + 关键链路人工验证 |

**Git 合并成功 ≠ 升级成功。** 语义冲突只能靠定制功能的回归测试发现，因此每个定制点必须有测试（见 §5）。

**质量属性优先级（冲突裁决序）**：**安全性 > 正确性/可靠性 > 可维护性 > 性能 > 功能丰富度**。适用于一切设计决策。语义是**冲突时的裁决顺序**——不是投入比例，也不是高级项可无限压低低级项；每个低级项有不可跌破的底线，跨级权衡（如以安全换功能）属例外，须按 §10 登记。

- **安全性是硬约束，不是可权衡项**：任何方案不得以牺牲安全换取其他属性；安全要求自身以威胁模型为边界，不无限外推。
- **正确性/可靠性**：宁缺毋错（与 §9 降级优先同源）；错误的代码比没有代码更糟——功能**做对**优先于功能**做多**。
- **可维护性**：在本仓具象化为本文目标（最小化升级成本）——为性能写晦涩代码、绕开上游公开 API 操纵内部结构等做法直接放大升级冲突面，默认禁止。
- **性能**：性能问题通常局部、可测量、可后期优化，默认不牺牲可维护性换性能；方案须做性能评估——不对性能造成不必要的影响，影响较大时须说明理由与权衡。
- **功能丰富度**：冲突时让步；质量债不得以功能进度为由累积。

## 2. 目录与术语

- **上游代码**：`src/chrys/`（各 tier 目录下的 `aixcoding/` 子目录除外）、`tests/`、`locales/`、`scripts/`、`docs/`、`pyproject.toml` 及根级配置。**上游测试（`tests/`）视同上游源码。** 上游目录内不落定制文件。
- **定制代码**（新增文件的唯一合法落点，均以 `aixcoding` 命名）：
  - `src/chrys/{tier}/aixcoding/` —— 产品定制代码（按 tier 落位，ADR-0011），进 wheel；档位判据见 R9 与 `DIRECTORY.md §3`
  - 仓库根 `aixcoding/` —— 纯开发资产：`tests/`、`docs/`、`mock/`、`tools/`，不进 wheel
- **定制测试**：唯一落点 `aixcoding/tests/`，独立于上游默认收集（显式运行命令见 §4，CI 执行点见 §9）。
- **定制点**：每一处获批的上游修改，或每一个独立定制模块。
- 落点判定、目录蓝图、tier/import 机制、mock 结构约定等细则见 `aixcoding/docs/standards/DIRECTORY.md`；决策理由与被否决备选见 `aixcoding/docs/standards/adr/`。

## 3. 硬规则（R1–R13，违反即返工）

- **R1 非侵入优先，必改时少而集中**：动手前先回答"能否完全不改上游？"（配置层 / 上游扩展点 / 运行时包装 / 独立模块），否决理由留档 design 对比表（条件变化可 revisit）。结论是必须改源码时，方案比选将**升级冲突面**（上游接触面积 = 文件数 × 行数 × 逻辑耦合度）作为硬性评估项，优先选择改动少而集中的方案：① 业务逻辑全部外置到定制模块，上游只留最小接线点（理想形态：数行钩子调用，不改上游既有逻辑流）；② 接线点数量与分布最小化，能一处不两处。边界：在上游结构允许的前提下——上游扩展点本身分散时，跟随其结构分散接线优于强行集中（后者引入更脆弱的语义耦合）。结论无论是否改源码，方案中用一句话说明理由。

  **迁移批次（阶段三起）执行细则**（细则单源在本条，design 模板与评审模板只引用不展开）：

  - **细则一（基线重审）**：迁移是在新基线上的重实现——旧分支挂点因基线漂移必然重审（可能失效或不再最优），照搬不是选项；
  - **细则二（逐行归属）**：R2 表**每行一条归属结论**（自下一份新签 design 起适用；既有已签认 design 不回溯改写），回答"这行能挪进定制包（`src/chrys/{tier}/aixcoding/`）吗"；行数最小（追版本成本）与归属正确（语义内聚；判据：该逻辑是否属该特性包的领域知识）双约束冲突时**归属优先**；函数体归位定制包、上游只留挂点是默认形态（实例：auth 批次 2 文件 `+41/−2` 收敛为 1 文件 `+16/−1`，git numstat 口径，见 `docs/batches/auth/design.md`）；
  - **细则三（消费方视野）**：公共逻辑沉为定制包公共 API，为后续批次复用铺路（反面教训：0.28 `_login_token`/`_catalog_token` 双份相似实现）。

  硬约束：上游对定制包的 import 须**函数内 lazy + 全吞错**（降级可接受时，如 auth 的 token 读取）；结构性接线（UI 基类继承等）失败应显式呈现，不适用全吞错；**直接依赖优于间接**（import 路径显性可见升级冲突）；**最小 ≠ 最隐**（显式小 diff 优于静默 patch；marker 与语义注释是必要开销）。
  验收线：R2 表逐行有归属答案（单文件收敛是 auth 特例非指标）；可观测性类特性（telemetry 等）"零主流程影响"权重高于行数最小。
  职责：design 作者必答（责任人签认时核对，见 4.1②）；评审抽查"是否逐行回答"（形式检查）。
- **R2 上游修改须审批**：对上游代码的任何改动（含 `tests/`、构建与打包配置如 `pyproject.toml` 的 packages）实施前，必须列出"改哪个文件、改什么、几行"，获负责人明确批准。AI 不得自行推断已获授权，不得以修 bug、顺手优化、重构为由绕过；被拒后回到 R1。
- **R3 标记注释**：获批的上游改动在改动处加**单行**注释：英文、简短、跟随上游注释风格，以 `AIxCoding` 关键词开头（注意大小写）并指向归属模块；自定义目录名统一为全小写 `aixcoding`。
  例：`# AIxCoding telemetry: emit tool events (src/chrys/kernel/aixcoding/tool_events)`
  （无方括号——对齐存量标记注释的实际格式；清单生成脚本按此匹配，数量以脚本扫描为准。）
  不使用多行 BEGIN/END 块标记——注释本身也是 rebase 冲突面。无法加注释的格式（JSON/二进制等）登记到定制清单；YAML/TOML 等支持 `#` 注释的格式正常打标记（可扫后缀清单见 `aixcoding/tools/_common.py`）。
  粒度（澄清，2026-10-28）：同一文件内**相邻**（成对行/同一代码块）的同特性改动**共用一个标记**；语义区分隔的改动各自标记——marker 的价值在 rebase 冲突现场的归属提示，相邻处合并零损失、逐处重复徒增清单噪音。
- **R4 新增文件入定制目录**：所有新增源码、测试、文档、脚本、mock 一律放 `aixcoding` 目录；进入 wheel 的定制代码落 `src/chrys/{tier}/aixcoding/`（按 tier 落位，ADR-0011），仓库根 `aixcoding/` 不进 wheel（`packages` 仅 `["src/chrys"]`，上游原状）。
- **R5 最小变更**：只改任务必需的内容。禁止顺手重构、格式化无关文件、改动无关注释、升级依赖、修改 CI。
- **R6 不覆盖他人工作**：发现工作区有未提交的他人改动时，停止并询问，不得覆盖。
- **R7 验证即证据**："完成/测试通过"必须附实际执行的命令与输出摘要；未运行的验证不得描述为通过；自生成测试不构成充分性证明。
- **R8 文档与登记同步**：改动落地时同步更新活文档与定制清单；**"决定不做"的事同样必须记录**（防止重复提议已否决方案）。
- **R9 定制代码依赖方向（按 tier 落位）**：定制产品代码按**实际依赖**落位 `src/chrys/{tier}/aixcoding/`（ADR-0011）：档位 = 四档（kernel/service/orchestration/app，按需建）中**能容纳其全部依赖的最低档**；kernel 档为默认最低档（零依赖与仅 foundation 依赖均落此），foundation 档不设；依赖做硬判据、语义做参考——放错层 `test_layering` 即红。kernel 档内互引必须**相对导入**。**例外（结构性挂接边）**：包内个别模块对宿主的向上挂接（进程入口、钩子注册，非业务库依赖）不改变整包档位——豁免通道（`_DAG_EDGE_ALLOWLIST`）已随 ADR-0013 整体移除，现无任何豁免通道：此类需求以**内联接线**替代（挂接模块落 app 档或入口直接调用），向上 import 即 `test_layering` 红；重建须 ADR + 责任人签认，不得以任何形式先行登记豁免。细则见 `DIRECTORY.md §3`。
- **R10 个人责任制（签认）**：每个任务/功能有唯一责任人，对其全部产出（需求理解、设计、实现、验证）负责。**需签认的文档**：`design.md` 与 ADR（决策档，仅 R2 清单变更须重签）、`self-review.md`（记录档，签一次追加不重签）；其余功能文档（requirements/test-plan/plan/verification）为活文档不签认。签认字段组：`责任人 / 状态 / 确认日期 / 确认意见（可选）`，**必须由责任人本人编辑并提交，AI 不得代填**。校验：`uv run python aixcoding/tools/check_docs.py`（覆盖 ADR、design、self-review 三类签认；design 含 R11 联动——依赖申请节存在且已确认时审批人/审批日期须非空；git blame 交叉核验与 CI 挂接为后续增强）；`git blame` 为抽查提供"谁签的、谁改的"事实依据。R2 的批准记录落盘于对应设计文档的签认与确认意见，不以聊天记录为凭。
- **R11 第三方依赖须审批**：定制代码（`src/chrys/*/aixcoding/` 与根 `aixcoding/` 全部资产）新增第三方依赖——运行时或开发用——**默认拒绝**，引入前须报批，申请说明：① 现有手段逐项排除（标准库 / 已有依赖 / 上游已有依赖，为什么都不行）；② 许可证兼容性；③ 供应链评估（维护活跃度、使用量、传递依赖树）；④ 锁定版本；⑤ 对 uv.lock 冲突面与离线打包的影响。申请落点为 design.md 的"第三方依赖申请"节（五项结构）；批准 = 获审批人（负责人或其指定人）同意，审批人/审批日期记入 **design.md 头部"新增第三方依赖审批"区域**（**经审批人同意后由责任人代填，AI 不得代填**；依赖清单变更须重新过审批人；谎报以抽查与追责兜底）；依赖引入通常命中 ADR 判定②（撤销代价高），应出 ADR。运行时依赖必改 `pyproject.toml`，同时是 R2 报批项；开发依赖不改上游文件，R11 即其唯一管控点。跟随上游升级带来的依赖变更（上游自身的增删）不在此列，走 §8；mock 专区维持 stdlib-only 更强约束（DIRECTORY.md §6）。决策理由见 ADR-0008。
- **R12 迁移批次方案重审**：迁移旧分支功能时，旧实现只是**内容索引**，不是方案承诺——① 选型必须对照目标基线的**同类机制现状**做同构跟随，不做形态平移（上游机制已演进时，旧形态可能破坏它）；② design 评审必含"目标基线下是否有比旧实现更好的方案"专题（结构 / 挂点 / 上游行数三维对比），无势均力敌更优方案时才平移旧实现，判定记录于 design。正例：tui 批次整体方案重审产出 silent check 挂点迁 MainScreen（app.py 归零、假设-2）；反例：0.28 徽标容器形态平移破坏 0.31 overlay 动态 margin 机制（tui 批次 self-review 留档，随其实施 PR 入库）。
- **R13 豁免须理由与批准**：豁免 = 对既有规则/门禁/约束的**个案性绕过**，封闭枚举：①架构豁免通道登记（DAG allowlist 类——现无通道，重建须 ADR+签认，见 R9 例外条款与 `DIRECTORY.md §3`；前瞻条款，通道不存在时永不触发）；②ruff 豁免新增（行内/文件级 noqa、pyproject per-file-ignores 新条目）；③测试豁免新增（skip/skipif/xfail 标记、deselect/路径排除、CI 分片排除）；④CI 门禁跳过（aixcoding 自有 workflow 内弱化门禁的动作：`if:` 条件禁用、continue-on-error、注释 job/步骤、门禁命令收窄如 --exclude；上游 CI 文件改动另触发 R2/R5）。枚举外新豁免形态——含 DIRECTORY.md 明文约束的个案例外，其正道是出 ADR 修规范本身而非留个案豁免——由责任人裁决入列。流程豁免（§4.2 免判定清单扩项、§6 微改动判定）不在此列，各归 ADR-0012 与责任人判定权既有管控。**默认立场：豁免是穷尽正当路径后的设计后备，不是实现选项**——约束挡路先按规则做（修代码/改写法/挪档/正确落位），确不可行才提议豁免。判据对照：正当后备如 RUF001 豁免定制测试的中文断言（规则与场景结构性冲突）；不正当如未查根因即 skip 偶发红测试（仅因不方便）。**新增豁免须责任人批准，AI 不得自行添加**（含修 lint/测试红时顺手加豁免——最高频偷懒路径）；呈报三要素：豁免形态、逐条理由（为何规则不适于此处，而非仅仅不方便）、已尝试的正当路径。留痕（注释是 git 可查的**授权凭据**，不是仅解释——PR body 可变非 git 对象，ADR-0012 同判）：豁免旁就地一行注释含**理由 + 批准指向**（PR 编号或批次 design/ADR），并列入 PR 变更导览"新增豁免清单"（§7）、评审逐条过目。档位分级（复用既有链条）：落上游文件的豁免叠加 R2；架构豁免通道重建叠加 ADR。存量豁免不溯及；工具化盘点（noqa/skip 清单增量进 CI 报告）为后续增强。决策理由见 ADR-0014。

> **R 系列变更的同步义务（防漂移）**：修改本节任一规则时，同步更新两处内嵌摘要——`SELF-REVIEW-HOWTO.md` §二 与 `PEER-REVIEW-HOWTO.md` §二 评审模板中的"评审背景"块（模板自包含，摘要滞后 = 评审 AI 用旧规则）。

## 4. 工作流（人机协作）

一人一功能：责任人对任务全权负责（R10），AI 代理执行。AI 的每个停等点，即责任人的出手点。

**流程分流**：标准改动走下方检查点与执行流；**微改动**（§6 豁免三条件全满足）免走本节与 §7 全流程——按 PR 描述（需求与方案要点）+ 验证证据 + peer review 交付即可，义务不减（R5/R7/R10 与 §5 测试义务不变）。

**分工总览**（地图；细则见 4.1 / 4.2）：

| 阶段 | AI 做的事 | 人（责任人）做的事 |
|---|---|---|
| ① 定需求 | 起草 requirements | 审意图与验收标准（活文档，不签认） |
| ② 裁方案 | 起草 design（备选/R2 清单/上游假设）+ 判定并起草 ADR | 审方案与 R2 清单，**签认 design 与 ADR（= R2 批准落盘；仅 R2 清单变更须重签）**；新依赖另过审批人（R11） |
| ③ 定测试 | 起草 test-plan（覆盖矩阵/行为锚定） | 确认（活文档，不签认） |
| ④ 实施 | 写码（R5/R3）、写测试、维护 plan | 抽查越权（扩了回炉 ②） |
| ⑤ 双 AI 自审 | diff 核对、跑验证记 verification；**换一个与主力开发不同的 AI** 评审→修复→复审循环至主要问题清零（`SELF-REVIEW-HOWTO`），产出 `self-review.md` | 确认主要问题已处置，**签认 self-review.md** |
| ⑥ 交付评审 | 组装 PR 描述（§7 结构） | 提 PR；**评审人**（另一人）按 `PEER-REVIEW-HOWTO` 裁决：上游逐行、blocker 逐条留痕 |

一句话：AI 干一切"写与跑"，机器门禁干确定性判断，人只定意图、拍决策、担责任（每功能 **2 次签认**：design 与 self-review；+ 1 次裁决 + 抽查）。

### 4.1 责任人检查点（人的工作流）

| 检查点 | 人做什么 | 签认 |
|---|---|---|
| ① 定需求 | 审 requirements：目标/非目标/验收标准是否为真实意图，指挥 AI 迭代 | —（活文档，不签认） |
| ② 裁方案 | 审 design：R1 非侵入结论是否成立（迁移批次含 R1 细则二逐行归属**已答**）、R2 上游清单是否可接受、上游隐式假设是否真实、ADR 判定是否合理（该出的出了没） | 签认 `design.md` 与 ADR——**此签认即 R2 批准的落盘** |
| ③ 盯实施 | 抽查 AI 是否越权扩范围（扩了 → 回炉重走 ②）；测试方案一并确认 | —（test-plan 活文档，不签认） |
| ④ 验交付 | 核 verification 证据：命令真实执行、结果支持验收标准（R7 的责任人核实） | —（不签认） |
| ⑤ 双 AI 自审后提 PR | 代码 + 已签文档 + **`self-review.md`（双 AI 评审产出）** + **变更导览** 同一 PR；**签认 `self-review.md`** = 评审结论经我确认、主要问题已处置 | 签认 `self-review.md`（记录档，签一次追加不重签） |

peer review 由另一人按 `PEER-REVIEW-HOWTO.md` 执行——**上游接触面逐行、blocker 逐条裁决（留痕于 PR）**、验证证据抽查；评审人**建议**换用与作者不同的 AI 辅助评审；**review 不转移责任**。

四条铁律（前三个为阶段停等点，第四个为全程物理闸门）：**方案未签，不动代码；R2 未批，不动上游；扩范围，停下重申请；git 写操作，逐条授权**——AI 每执行一条 git 写操作即停下汇报、等下一条明确指令再继续；聊天中的认可一律是讨论性反馈，进入实施的唯一信号是 design.md 签认字段落盘（ADR-0012）。

签认分档（R10 补充）：

- **决策档**（`design` / ADR）：签认后**仅 R2 清单（上游改动批准对象）变更时须重签**；其他内容变更不重签（git 可查）——上游批准不可被静默修改是唯一硬底线；
- **记录档**（`self-review.md`）：签认一次，后续追加评审记录不触发重签；
- **不签认**（`requirements` / `test-plan` / `plan` / `verification`）：活文档，随时更新，git 留痕；其质量由 design 签认、双 AI 评审与测试本身保障。

### 4.2 AI 执行流

1. **接任务** → 先读相关活文档（尤其 plan.md 的状态、挂起事项），确认不重复已否决或已挂起的方案。随后按**开工判定单协议**（ADR-0012）呈报并停等：**情况（分析结果）+ 建议（附理由）+ 选项（走完整管线 / 申请豁免，两条路径恒呈现，不因核对结论隐藏其一）**，责任人裁决（可推翻 AI 任一判断，含豁免三条件核对结论本身）。**免判定清单**（封闭，规范预定义；AI 只做机械匹配、不得现场判断任务归入，拿不准即停等）：① 活文档追加与常规更新（verification / plan / test-plan / requirements；design、adr/、self-review 正文修改排除）；② 只读操作（读文件、`git status/log/diff/show/fetch`、跑测试）；③ 已签认方案范围内的实施动作（匹配口径：该动作与 design 变更清单 / R2 表逐项对应，对不上即停等）——清单内任务一行报备（做什么 + 清单项编号）后直接执行，用户明确指令过的任务无需报备（指令即知情）。
2. **方案** → 涉及上游改动时停在方案阶段等批准（R2；批准落盘 = 责任人签认 design/ADR，见 4.1②）。方案包含：目标与验收条件、非侵入式评估结论（R1）、将改/将增文件清单、验证方式。
3. **实施** → design 未签认不得动代码（4.1 铁律）；最小变更（R5），上游改动带标记（R3）。
4. **自检** → `git diff` 逐文件核对：无越权文件、无意外产物、标记齐全；运行验证。**统一入口**（local-verify 批次）：`uv run python aixcoding/tools/verify.py --smart [--paths ...]`——委托上游 Smart Test + 无条件完整定制套件，任一失败非零退出（直接跑变体：`uv run pytest aixcoding/tests -m "not integration and not gc_calibration"`；纯上游快速反馈：`--upstream-smart`）。
5. **双 AI 自审（强制）** → 按 `SELF-REVIEW-HOWTO.md`：**换一个与主力开发不同的 AI** 独立评审（checklist 内嵌于其指令模板），责任人逐条拍板修/不修（不吹毛求疵：blocker 必修，次要问题可不修），评审→修复→复审（只审增量）循环至主要问题清零，产出 `self-review.md`（记录评审 AI 标识、blocker 处置与未修项），责任人签认后随 PR 提交。评审模型见 ADR-0007。
6. **交付报告**（格式见 §7）→ **登记**（更新定制清单与活文档）。

执行中若发现需扩大改动范围（新增上游文件、超出批准行数）：停下，重新申请。

## 5. 定制点登记（design.md 点级登记表 + 对账命令，ADR-0015）

登记是升级时的地图。**语义登记在各批次 design「定制点登记预告」表——点级，一行=一个定制点
（孪生组同文件同文本 marker 合并一行：区间 id + 预期计数），可选批次锚注段共享 anchor/risk；
代码事实来自 marker 扫描——禁止手工维护代码事实**（手写台账必然漂移）。对账工具
`aixcoding/tools/gen_customizations.py`：默认 check（只读对账，零文件写入）、`--strict`
（CI 姿态：孤儿登记升级为 error）、`--report`（stdout 全景视图，升级时点快照附 verification.md）。
校验语义：marker 无登记 = error（先 design 后代码闭环）；孤儿登记本地 warning / CI strict error；
id 全局唯一（含退役号高水位，`C###` 为沟通标识非主键，分配=历史最大号+1 永不复用）；
匹配键=(落点, marker 锚) 前缀 + 最长锚优先。集中产物 `CUSTOMIZATIONS.md` 已随
customization-registry 批次退役（衍生物不落盘，freshness 义务随之取消）；登记行改动属
R10 重签范围。格式契约见 `standards/templates/design.md`。

每个定制点一行（字段契约与 `standards/templates/design.md` 一致）：

| 字段 | 说明 |
|---|---|
| `id` | `C###` 沟通标识（主键=落点+marker 锚，非 id） |
| `落点` | marker 所在上游文件 posix 路径（不含行号） |
| `marker 锚` | marker 注释正文前缀（同文件内唯一区分） |
| `预期计数` | 孪生组大小（同文件同文本 marker 合并行；默认 1） |
| `anchor` | 依赖的上游接口/符号——升级时重点核对（可引用批次锚注段） |
| `risk` | 低（独立模块）/ 中（依赖非公开行为）/ 高（改核心源码、构建配置） |
| `removal_condition` | 淘汰裁决触发条件（判据类别见 UPGRADE-RUNBOOK §5 附录；命中 ≠ 可删） |

上游基线（开发时基于的上游版本）由 `UPGRADE-RUNBOOK.md` 头部「当前基线」节全局承载，
无逐点 `upstream_base` 字段（customization-registry 批次起，ADR-0015）。

高风险定制点必须有自己的回归测试与回滚说明。

**行为锚定测试**：每个 `anchor` 至少配一个真实调用所依赖上游符号、断言其行为的测试——**禁止 mock 该符号本身**（mock 掉锚点，测试就永远检测不到上游行为变化，语义冲突检测形同虚设）；mock 只允许用于锚点之外的协作对象。这是"每个定制点必须有测试"从**有**到**有效**的判定标准。

## 6. 功能文档管线

每个功能一份文档目录：`aixcoding/docs/batches/<feature>/`（小写中划线命名；除 `standards/` 与根文件外全部批次/专项目录平铺于 `batches/` 下，不再按分类维度分层——依据 ADR-0016），必备文件：

| 文件 | 职责 | 时机 |
|---|---|---|
| `requirements.md` | 背景与问题、目标/非目标、用户场景、验收标准 | 开工前 |
| `design.md` | 方案概述、备选对比、R2 上游改动清单、**对上游隐式行为的假设**、风险与回滚 | 开工前（方案停等，见 §4） |
| `adr/`（有则建） | 决策记录（判定见下） | 设计中触发 |
| `test-plan.md` | 测试策略、覆盖矩阵（每条验收标准至少一行）、异常与降级路径 | 实现前 |
| `plan.md` | 任务清单/状态/续接入口（AI 每次接手先读） | 持续维护 |
| `verification.md` | 验证证据：命令 + 输出摘要（R7 的落盘形态，追加不删旧） | 每次验证 |
| `self-review.md` | **双 AI 评审产出**：评审 AI 标识、轮次、blocker 处置与未修项（见 `SELF-REVIEW-HOWTO.md`） | 提 PR 前；记录档签认一次 |

- 模板：`aixcoding/docs/standards/templates/`，文档由 AI 起草、责任人审阅迭代并签认（R10）。
- **INDEX 登记**：创建批次目录时同步在 `aixcoding/docs/INDEX.md` 增加一行（目录/类型/一句话简介）——纯静态导航，不承载状态、PR 号、日期等动态事实数值（ADR-0016）。
- **厚度与规模成正比**：小功能按模板占位符极简填写（每件数行）即可，条件性章节按其标注取舍（如 design.md"无上游改动则删除本节"），骨架文件不省——管线一致性优先于单件厚度。
- **微改动豁免**：同时满足 ①不涉及任何上游文件 ②不触发 ADR 判定 ③变更限于定制目录内且规模小（约百行以内）的改动，免走文档管线与 §4/§7 全流程。**豁免判定权归责任人**：AI 依开工判定单（§4.2）提议、责任人裁决，AI 不得自行判定豁免跳过管线（ADR-0012）——PR 描述写清需求与方案要点、贴验证命令输出；**双 AI 评审保留**（精简模板，不含 R2 比对；结论贴 PR 描述即可，免 `self-review.md` 文档）；peer review 仅做缺陷模式抽查 + 验证输出必看。**豁免的只是文档形态，义务不豁免**：R5（最小变更）、R7（验证即证据）、R10（责任人）、§5 测试义务（新增独立定制模块仍须有测试）不变。理由：升级摩擦来源于上游接触面，微改动接触面为零，流程重量应与摩擦风险成比例。豁免裁决指引：将来回滚/升级要独立追溯吗 / 有需对照核验的验收标准吗 / 半年后无背景文档能看懂意图吗——任一"要/有/不能"走管线；纯机械变更（typo/格式/明显单行修复）直接豁免。
- **ADR 判定 checklist**（任一"是"即出；粒度是**决策**不是功能，一个功能可能 0 个或多个）：
  1. 有被认真考虑但否决的备选方案；
  2. 撤销代价高（依赖方向/目录落点/数据格式/对外契约）；
  3. 约束未来工作模式，后来者会问"为什么这么做"；
  4. 依赖上游非公开接口或行为（另登记定制清单 `anchor`）。

  反面清单（不出 ADR）：模块内实现选择、唯一合理路径的照规范执行、纯文档修正。
- **ADR 分池**：全局/架构级决策 → `standards/adr/`（不随特性消亡）；功能级决策 → `batches/<feature>/adr/`（特性淘汰随目录归档）。编号各自独立。
- **ADR 编号**：`NNNN-标题.md`，取目录现有最大编号 +1；编号被引用后不改号；并行撞号罕见且必然被 git 同名冲突暴露，暴露早期重新编号即可——不做预防机制。
- **规则与 ADR 的边界**：规则（约束行为的条文）唯一维护处是规范条款（本文与 `DIRECTORY.md`）；ADR 是**自包含的决策时点快照**——决策节完整记录当时定的机制内容，写定不改。规范演进**不回改 ADR**：重大规则变更出新 ADR，旧 ADR 标"被取代"形成决策链。规范可引用 ADR 作为理由出处（安全方向）；ADR 指向规范仅作导航注记（"本文为快照，现行以规范为准"），不作为决策内容的一部分。
- **决策更新的处理**：决策实质变更（结论反转/机制变更/前提失效/适用范围变化）→ **新建 ADR 取代**，旧 ADR 仅改头部状态、正文一字不动（被取代标注不触发重签）；新 ADR 背景必须引用旧 ADR 并说明"什么变了"。原地修改仅限非决策性修正（错别字、失效链接、不改变结论的背景补充）。检验法：修改是否会让"当时为什么这么定"的记录失真？
- **ADR 的举证态度（防将错就错）**：既有 ADR 提供的是**默认权重而非终审**——"存在 ADR"不构成遵循理由，构成的是推翻时的举证义务：以错误认知为前提制定的 ADR，有足够合理的理由就应按上条取代流程改掉，不得通过解释将错就错。正例：ADR-0002 的 tui 单点特判因落地死结被 ADR-0011 取代；ADR-0005 的"不引入 msg()"因 `MessageRef` 强类型现实被 ADR-0010 取代。评审与实施遇到"ADR 要求这么做但现状明显不合理"时，触发本条并按 ADR 判定②重估。
- 文档语言：中文（团队工作语言）。代码与注释语言：跟随上游（英文）。

## 7. 交付报告固定格式（载体：PR 描述）

**交付报告即 PR 描述本身**，按以下结构填写——"变更导览"与"self-review 摘要"是其组成部分（§4.2 步骤 5），**不另写报告文档、不重复撰写**；各项直接引用功能文档目录的对应文件。微改动（§6 豁免）仅保留导览 + 验证输出。

**CI 证据归属**：CI 结果的证据是 **PR checks 本身**（GitHub 永久可查：run 链接、日志、结论），不回写仓库——PR 创建后**零追加留痕**（唯一例外：code review / CI 发现问题后的功能修复 commit，属正常迭代非留痕）。`verification.md` 只落盘本地验证的命令与输出。（2026-10-26 负责人决策；避免"追加留证→触发 CI 重跑→再留证"的递归。）

```
1. 需求完成情况（对照 requirements.md 验收标准，逐项勾验）
2. 变更导览（意图一句话 / 核心区域 / 机械性变更清单 / 新增豁免清单（R13）逐条列出，无则省略；git stat 摘要，逐项标注 上游/定制——上游项指向 design.md 签认，即 R2 审批对应关系）
3. 实际执行的验证命令与结果（引用 verification.md 最新一节）
4. `self-review.md` 摘要（双 AI 结论、blocker 处置与未修项）与未验证事项、已知风险
5. 回滚方式与文档/定制清单更新情况
```

## 8. 升级流程（跟随上游新版本）

> 操作展开版（分支拓扑与镜像纪律 / 冲突高发区对照表 / 工具命令序列 / 已知坑速查）：`aixcoding/docs/standards/UPGRADE-RUNBOOK.md`。

**升级节奏（债务控制）**：每次上游发布后评估跟进；**不跟进（跳过版本）须显式记录理由与计划跟进点**——升级间隔越长，三层冲突的合并成本越高，长期不升级是需要显式决策的风险状态，不是默认态。当前所基于的上游版本（即升级 diff 区间的起点）记录于 `UPGRADE-RUNBOOK.md` 头部「当前基线」节（customization-registry 批次起；随每次升级完成更新）。

按序执行，产出升级报告：

1. 记录目标版本与上游 diff 区间。
2. **文本层**：合并/移植，逐个冲突点对照定制清单。
3. **结构层**：清单中每个 `anchor` 核对上游是否仍存在、签名/语义是否变化。
4. **语义层**：重跑全部定制测试 + 关键链路人工验证。
5. **淘汰检查**：上游是否已实现等价能力——命中 `removal_condition` 的定制列为**淘汰候选**，
   **禁止自行删除**：上游实现按上游一般需求做的，与我方按内部需求定制的实现很可能不完全一样
   （功能名相似 ≠ 等价），须逐点产出对比分析与处理意见、交责任人裁决，获批后方可删
   （2026-10-31 责任人指示；每次升级同时交付：冲突点全清单+处理意见、定制化改变清单——
   需新增/建议删除/需适配，全部交责任人裁决并文档留痕）。
6. 更新各定制点 `upstream_base`，重评 `risk`。

## 9. 定制代码自身约束

- **降级优先（宁缺毋错）**：定制功能依赖缺失或环境异常时 lazy import + 降级，不得影响上游主流程；上报数据字段宁缺勿错。**降级与异常必须可查、可追溯**（问题发生时有据可依），具体可观测性机制（日志、状态、诊断入口等）不预设结论，待专项讨论定稿后补充本条。
- **日志分层口径（2026-11-04 定稿，catalog-auth-gating 方案六；2026-11-05 补例）**：`aixcoding.*` 主卷（`aixcoding.log` + 日志面板）只承载**用户功能事件**（登录/登出状态与结果等人话信息；**用户可操作的配置错误亦属用户功能事件**——如停用环境变量误配的 WARNING，先例：logging-routing-fixes 批次 D 项）；**技术事件一律仅写 `aixcoding.detail.log`**；用户功能事件**双写**两卷，使 detail 卷成为开发人员的自包含全量卷（单卷即可理解时序、重现问题，无需两卷对照）。新批次/新埋点按此归类，不得向主卷写技术记录。
- 依赖方向：定制适配层可被上游显式调用（获批埋点），定制业务不得让上游反向依赖具体实现；`src/chrys/*/aixcoding/` 内部的分层约束见 R9。
- 新第三方依赖默认拒绝、报批后引入，管控细则见 R11。
- 定制测试独立于上游默认收集（`aixcoding/tests` 显式运行；CI 执行点为独立 workflow `.github/workflows/aixcoding-tests.yml`——**规划中待建**（`batches/restructure/plan.md` U3），建成后覆盖 `aixcoding/` 的 lint 与 mock 契约测试），不修改上游测试基础设施来适配定制测试，不 import 上游 `tests/support/` 设施（可阅读、复制，不可依赖）。
- 自建 mock 统一放 `aixcoding/mock/`，结构强约束见 `DIRECTORY.md`；每个 mock 必须有契约测试（`aixcoding/tests/mock/`）。
