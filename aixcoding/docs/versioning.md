# fork 版本与发布策略（versioning）

> 定位：fork 版本号、内部发布与 CHANGELOG 的唯一约定。属阶段二第 5 项（一页决策，实施后置）。
> 状态：已确认（负责人 2026-10-25 对话中提出四段方案并确认）。

## 1. 版本号方案：上游三段 + fork 第四段

格式：`<上游版本>.<fork序号>`，如 `0.31.0.1`。

- 前三段：**严格等于**上游 release 版本，绝不自行改动——基线身份一眼可辨；
- 第四段：fork 在该基线上的发布序号，从 **1** 起；**基线升级时重置为 1**（例：`0.31.0.1 → 0.31.0.2 →
  上游升 `0.32.0` → `0.32.0.1`）；无位数上限（PEP 440 逐段数值比较，`0.31.0.10 > 0.31.0.9`）。
- 排序语义：上游基线优先、fork 序号次之，与"追版本"心智完全一致。

依据：四段是 PEP 440 合法 release 版本（pip/uv/hatchling 全兼容）；备选 `0.31.0+aix.1`
（local version）被否决——含 local 段的版本不参与依赖解析候选，未来内部制品库场景
`pip install` 选不中；fork 独立三段（1.0.0）被否决——丢失上游基线信息。

## 2. 分发约定

- 分发名/wheel 名**保持上游**（`iCode-TUI` / `icode_tui`）：内部覆盖安装语义清晰，
  四段版本号即身份标识，不需要第二个包名。分发身份裁决记录于
  `standards/adr/0021-分发身份沿用iCode-TUI.md`（签认状态以该 ADR 头部为准）。
- 首个 fork 版本号出现在**第一个含定制产品代码的内部发布**（预计阶段二完成后的
  `0.31.0.1`；基线届时以实际上游版本为准）。
- 内部发布通道与离线打包：沿用上游构建脚本体系，实施细节按真实分发需求后置补记于本文。

## 3. 上游 release workflow 注意（R2 关联）

上游 `tag-release.yml` 监听 **main 分支** `pyproject.toml` 变更自动打 tag 并触发 CD
（PyPI 发布需 secrets，fork 环境发不出去，但会产生无意义 tag）。当前分支 `main_aixcoding_cli`
≠ main，**不会触发**。约定：

- 未来若将定制分支合并/改名为 main，须先处理 `tag-release.yml` / `cd.yml` 的触发条件（该改动属 R2 报批）；
- 修改 `pyproject.toml` 的 `version` 字段属上游文件改动，首次上版本号时随 R2 一并报批。

## 4. CHANGELOG 约定

`aixcoding/docs/CHANGELOG.md`，每 fork 版本一节，倒序：

```
## 0.31.0.1（日期）
- 上游基线：0.31.0（无升级，初始基线）/ 上游变更摘要或链接
- fork 变更：按特性列（诊断包、四工具…），含 R2 上游改动清单引用
```

目的：任何人拿到一个内部版本，能立刻回答"基于哪个上游、比上个内部版本多了什么"。
