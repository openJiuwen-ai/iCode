# fork 版本与发布策略（versioning）

> 定位：fork 版本号、内部发布与 CHANGELOG 的唯一约定。属阶段二第 5 项（一页决策，实施后置）。
> 状态：临时决定（负责人 2026-11-09）——版本号**暂保持上游三段**、与基线一致；
> 四段/系列等扩展方案为候选、**未最终裁决**，暂不出 ADR。

## 1. 版本号方案：当前口径＝上游三段（临时）

- `pyproject.toml` 的 `version` **严格等于**上游 release 版本（当前 `0.35.1`），**不引入
  fork 第四段**；基线升级只随上游同步三段（version 行变化为上游自身变更，不算我方改动）。
- fork 定制身份在版本号上**不体现**，由 CHANGELOG、分发来源等承载；同一上游基线下的多次
  内部发布在版本号上暂无法区分。

### 候选扩展（未裁决，暂不出 ADR）

此前讨论过的四段与"系列"方案暂缓、留档备查；是否启用及如何启用待后续决策
（届时按 `standards/DEVELOPMENT.md` §6 走完整管线并配套 ADR）：

- **四段**：`<上游三段>.<fork序号>`（如 `0.31.0.1`）——前三段严格等于上游，第四段为 fork
  在该基线上的发布序号（从 1 起、基线升级重置为 1）；PEP 440 合法 release 版本（pip/uv/hatchling
  全兼容）。fork 独立三段（如 `1.0.0`）已否决——丢失上游基线信息。
- **测试/候选**：pre-release 段 `rc`/`b`（如 `0.34.0rc1`），pip 默认不选中（除非 `--pre`）。
- **实验系列**：local 段 `+exp.<系列名>.<序号>`（如 `0.34.0+exp.telemetry.3`），用于长期并行
  实验线（如 telemetry 直改方案与 Session 分析方案并存）。注：local version 作为**主发布版本号**
  已否决（不参与依赖解析候选，制品库 `pip install` 选不中）；用于**实验系列**时该特性恰可
  防误装，二者区别待最终裁决确认。

## 2. 分发约定

- 分发名/wheel 名**保持上游**（`iCode-TUI` / `icode_tui`）：内部覆盖安装语义清晰，不需要
  第二个包名。分发身份裁决记录于 `standards/adr/0021-分发身份沿用iCode-TUI.md`
  （签认状态以该 ADR 头部为准）。注：ADR-0021 中"四段版本号即身份标识"的论据随本临时决定
  暂不成立，待版本号方案最终裁决后同步修订。
- 首个含定制产品代码的内部发布沿用上游三段版本号，不另行计数。
- 内部发布通道与离线打包：沿用上游构建脚本体系，实施细节按真实分发需求后置补记于本文。

## 3. 上游 release workflow 注意（R2 关联）

上游 `tag-release.yml` 监听 **main 分支** `pyproject.toml` 变更自动打 tag 并触发 CD
（PyPI 发布需 secrets，fork 环境发不出去，但会产生无意义 tag）。当前分支 `main_aixcoding_cli`
≠ main，**不会触发**。约定：

- 未来若将定制分支合并/改名为 main，须先处理 `tag-release.yml` / `cd.yml` 的触发条件（该改动属 R2 报批）；
- `pyproject.toml` 的 `version` 字段属上游文件：随上游基线同步三段为上游自身变更（无需 R2）；
  未来若主动引入 fork 版本号（四段/系列）改 `version`，属 R2 报批。

## 4. CHANGELOG 约定

`aixcoding/docs/CHANGELOG.md`，每个内部版本一节，倒序：

```
## 0.34.0（日期）
- 上游基线：0.34.0 / 上游变更摘要或链接
- fork 变更：按特性列（诊断包、四工具…），含 R2 上游改动清单引用
```

目的：任何人拿到一个内部版本，能立刻回答"基于哪个上游、比上个内部版本多了什么"。
