# ADR-0001：护栏出厂写入范围改为不限制

## 背景

`batches/guard-hooks` 按「与 0.28.0 final 等价迁入」落地，规则包里
`settings.write_scope.allow_outside_workspace` 为 `false`，即出厂状态下
`T-FS-01`（文件写入白名单）与 `T-SHELL-05`（shell 写到工作区外）会拦截任何
工作区外写入，仅放行 `$TEMP/icode-session-*`，且 `**/docs/**`、`**/help/**` 只读。

现场反馈的直接矛盾：内网开发机上，构建脚本、`uv` / `npm` 缓存、编辑器临时产物
普遍写到家目录或 `/tmp`，被这两条规则拦下；而放宽的唯一办法是改 `rules.json`，
该文件每次启动被重新安装覆盖——**改了等于没改**。

本批次移植同事的运行期开关（`guard_state.json` + `guardctl`）后，写入范围第一次
具备现场切换能力。此时出现一个必须先定的问题：**出厂默认到底是拦还是不拦**。

## 决策

出厂**不拦**：`rules.json` 的 `settings.write_scope.allow_outside_workspace` 取 `true`。

- 出厂状态：写到工作区外放行，`T-FS-01` / `T-SHELL-05` 不触发；
- 需要收严时由现场执行 `guardctl workspace restrict`，写入范围判定随即按工作区
  + `temp_prefixes` + `readonly_globs` 生效（含符号链接 / junction 的规范化解析）；
- 该裁决同时意味着 `batches/guard-hooks/requirements.md`「规则内容零增删改」
  被本批次显式覆盖一行——这是**有意的口径变更**，不是回归。

## 理由

- 0.28.0 final 的 `false` 是在**没有现场切换手段**的前提下定的：出厂值就是唯一值，
  定严一点更安全。开关落地后这个前提消失，出厂值可以按"最常见的正确行为"定。
- 内网现场的写入路径以家目录 / 临时目录为主，拦截的边际安全收益低于误报成本；
  真正的敏感面是**读**（凭据、私钥、逆向工具产物），由 `T-FS-02` / `T-FS-03`
  的黑名单覆盖，不受本决策影响。
- 若定为 `false`，需要管理员先知道 `guardctl workspace allow` 才能正常干活；
  首装即被拦的体验会直接导致"把护栏整体关掉"，反而更差。

被否决的备选与死因：

- **保持 `false`（与 0.28 等价）**：默认最安全，但首装误报概率高，且需要现场
  先学会放宽命令；等价迁移的验收标准虽可复用，但与现场可用性冲突。
- **出厂 `true` 且不提供收紧手段**：等于永久放弃这两条规则，`T-FS-01` / `T-SHELL-05`
  成为死规则（原方案文件级开关的处境）。
- **按工作区自动判定（有 `.git` 才限制）**：隐式行为，现场不可预期，且判定依据
  不稳定（子目录、裸仓库、多工作区）。

## 后果

- 出厂安全口径放宽一条：写到工作区外不再拦截。后来者若只看规则包会疑惑
  `T-FS-01` 为何不生效——本 ADR 与 `SWITCHES.md` 是解释入口。
- 测试义务：涉及写入范围的既有用例必须显式构造"限制态"（
  `config_with_write_scope(restricted=True)` / 部署前写限制态 `guard_state.json`），
  不得依赖出厂值；否则本决策反转或用例迁移时会出现假绿。
- 文档义务：`OPERATIONS.md` 与 `SWITCHES.md` 必须写清"出厂不限制、如何收紧"，
  `MANUAL_TESTS.md` 的写入范围用例需带 `workspace restrict` 前置。
- 回滚：改回 `rules.json` 一行 + 撤销测试前置即可，无数据迁移、无对外契约影响。
